## 0. Storage/data directory permissions

Closes `docs/SECURITY_SWEEP_2026-09-23.md` finding **L20** (blob dirs/files created
under the ambient umask). Pattern taken from `nvr-daemon`'s `blob_crypto.cpp` /
`tls.cpp`: `chmod 0700` a directory immediately after `create_directories`, `chmod 0600`
a file right after writing it.

- **Per-user isolation at the OS level, on top of the existing E2E encryption**: each
  user's blob directory (`data/storage/<user_id>/`) already only ever holds
  AES-256-GCM ciphertext — that part's done (E2E Phase 2, see `docs/SECURITY.md`).
  What's missing is locking the *directory* itself down to `0700` right after
  `FileStore` creates it, so another local account on the same box can't even list a
  user's filenames/blob keys, let alone read the (already-encrypted) bytes. Same for
  each file as it's written (`0600`).
- `src/storage/file_store.cpp` — the per-user blob directory and each blob file.
- Wherever `DB_PATH`'s parent directory gets created (`src/main.cpp`).
- Mechanical, low-risk, no interface changes. Do this first.

## 1. Self-signed HTTPS, in-daemon — no nginx

Tailscale reaches the box directly; cloud-serv terminates its own TLS the way
nvr-daemon does, instead of "front with a reverse proxy" (the current
`docs/ROADMAP.md` line).

- Crow already supports this: `CROW_ENABLE_SSL` + `App<...>::ssl_file(cert, key)`.
  `-lssl -lcrypto` are already linked (Makefile). One Makefile flag + a few lines in
  `main.cpp` wires it — no new dependency.
- Cert generation: same *idea* as nvr's `core/tls.cpp` (self-signed EC P-256, 10y,
  SAN built from the box's own local IPv4 interfaces via `getifaddrs`), but written
  natively against the OpenSSL C API cloud-serv already links (`security/crypto.cpp`
  is the existing precedent) rather than nvr's `fork()+execvp()` of the `openssl` CLI
  — no new runtime dependency on the `openssl` binary.
  - `chmod 0600` the key, `0700` its parent dir (same as #0).
  - New config: `TLS_CERT_PATH`, `TLS_KEY_PATH` (mirrors nvr's naming).
- **The Tailscale-IP-in-SAN gotcha** (nvr's `DEPLOYMENT.md` flags this exact issue):
  if the cert is generated before Tailscale is up, or before the tailnet IP is known,
  the SAN won't include it and browsers will reject the cert over the tailnet.
  **Decided:** auto-detect at startup. Query the box's actual Tailscale IP (read
  `tailscale ip -4` if the CLI is present, or fall back to scanning interfaces for the
  `100.64.0.0/10` CGNAT range Tailscale uses) and if it isn't already in the existing
  cert's SAN, regenerate the cert to include it before binding. Covers the "Tailscale
  configured after the cert already existed" case with no manual step.
- **Setup script**: a `scripts/setup-tailscale.sh` (mirrors nvr's `deploy.sh` pattern)
  that automates as much of the Tailscale side as reasonably can be: installs the
  `tailscale` package if missing, runs `tailscale up` (interactive auth is unavoidable
  — it opens the login URL), and once connected, prints the tailnet IP/hostname for
  the operator to drop into config. cloud-serv's own startup regen (above) then picks
  it up automatically on next launch — the script's job is getting Tailscale itself
  running, not touching cloud-serv's config.
- Once this lands, the session cookie's `Secure` flag (sweep finding **M8**) can just
  always be `true` — no more conditional logic, since there's no longer a plain-HTTP
  path to the app at all.
- Doc updates: `docs/ROADMAP.md` "Before exposure" section, `docs/SECURITY.md`'s
  closing note about transport.

## 2. Login/session hardening batch

This is cloud-serv's own multi-user system — not ported from nvr (nvr is
single-credential by design, nothing to port here beyond the ideas already folded into
#0/#1). Closes sweep findings **H1, M6, M7, M8, M9, M10**:

- **H1** — fix `rate_limiter.cpp`'s XFF parsing direction (walk right-to-left, skip
  trusted proxies) — this one gates the others, since it currently lets an attacker
  spoof their rate-limit identity and defeat every throttle below.
- **M6** — per-account login throttling (on top of the existing per-IP limiter).
- **M7** — stop `/register` leaking email-registration status via `409` vs `200`.
- **M8** — cookie `Secure` (falls out of #1, just needs the conditional removed).
- **M9** — drop the redundant session token from `localStorage`; the web client relies
  on the HttpOnly cookie only (already supported — `request_auth.cpp`'s cookie path).
- **M10** — API-key management endpoints require session auth, not another API key
  (closes the "leaked key can mint child keys that outlive its own revocation" gap).

## 3+4. Functionality + full UI redesign (combined)

Functionality = `docs/ROADMAP.md`'s "Next" list. UI = full redesign, not incremental
fixes — current state per your words, kept verbatim as the brief: *"the ui looks like a
kid took lego bricks and hammered them together."* These are one effort because the
functional model (how a file gets fetched/decrypted/rendered) determines the UI's
structure (what a preview surface, a player, a file-type grid actually need to do) —
designing the visuals first and retrofitting the streaming logic into it would just
reproduce the current mismatch.

**Functional backbone (from ROADMAP):**
- **Streamed decrypt for video** (ROADMAP Phase 4): today `fetchPlaintext` downloads
  and decrypts a file **completely** before anything plays (`web/app.js:208-215`,
  `:1011-1024`) — confirmed while reading the code just now. Replace with
  MediaSource-based playback: fetch + decrypt frame-by-frame (the 1 MiB AES-GCM
  frames already exist on the wire, per `CRYPTO_SPEC.md`) and feed the player as
  bytes arrive, so a multi-GB video starts playing immediately and seeks without ever
  holding the whole file in memory. Nothing is written to local disk either way
  (Blob URLs are in-memory) — the change is about *not waiting for the whole file*,
  not about storage location.
- **Universal file-type support**: today `previewKind` (`web/app.js:966-973`) only
  renders image/video/audio/pdf/text inline; everything else falls back to a bare
  "no preview, download" card (`previewCard`). Every file type needs a first-class
  presentation — not necessarily inline-rendered (a `.zip` isn't going to preview),
  but a *designed* card/icon/metadata view per category (archives, office docs, code,
  fonts, etc.), not one generic fallback for "everything else."
- **Client-side search/sort/categories** (ROADMAP Phase 3) — required since names and
  mime are already opaque to the server; categories need to derive from the decrypted
  mime client-side.
- **Recovery-key login flow** (ROADMAP) — wrap/unwrap is verified, the UI path
  ("forgot password → unlock with recovery key → re-wrap DEK under a new password")
  isn't wired in yet.

**UI redesign:**
- **Direction (settled): closer to Google Drive**, with feature touches layered on as
  we get to each one rather than locked in up front. Keep the current IA's bones
  (sidebar + grid/list + breadcrumbs already follow the Drive shape) but this is a
  real visual redesign pass — consistent spacing/type/color/component system — not a
  bugfix pass on the existing "lego bricks" implementation, and the preview/player
  surfaces get rebuilt for real inline rendering + streaming per file type rather
  than retrofitted onto the current grid tile / modal.
- Concrete look-and-feel choices (exact palette, density, animation, etc.) get decided
  file-type-by-file-type / screen-by-screen as we build each piece, not all up front.
